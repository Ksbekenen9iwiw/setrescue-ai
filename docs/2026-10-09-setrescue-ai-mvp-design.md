# SetRescue AI — MVP Design Specification

Date: 2026-10-09
Status: Draft for user review
Scope: Local hackathon MVP

## 1. Product Summary

SetRescue AI is a local-first production readiness and adaptive recovery system for film/video production teams. The MVP focuses on two capabilities:

1. PREVENT — detect readiness gaps before shooting by analyzing Script, Shot List, Call Sheet, resource availability, quality requirements, and contingency readiness.
2. RECOVER — when production conditions change, generate verified recovery options that remain shootable under current constraints and compare their time, cost, and schedule-disruption trade-offs.

The primary user is a Production Manager. The MVP has no authentication and runs locally on a Windows laptop.

The key product principle is:

> AI interprets and explains. SetRescue calculates and validates.

The system must not ask an LLM to directly create the final shooting schedule, calculate authoritative costs, or silently convert AI suggestions into hard constraints.

## 2. Core Differentiation

SetRescue is not positioned as a generic AI rescheduler. Its intended differentiation is the connection between pre-production readiness and runtime recovery:

- PREVENT works at shot-level detail to identify incomplete or risky production requirements.
- Confirmed requirements are persisted in a shared Production Dependency Graph.
- RECOVER uses those same confirmed dependencies to decide whether a scene is actually shootable under current production conditions.
- Recovery plans are generated by a deterministic constraint solver and are rejected or downgraded to draft if hard constraints cannot be satisfied.
- Cost and time impacts are calculated by internal engines rather than invented by AI.
- After approval, SetRescue creates a new schedule version, updated call sheet, and crew update workflow.

A concise positioning statement is:

> We don't just reschedule your shoot. We help ensure the next plan is actually shootable.

## 6. PREVENT Engine

### 6.1 Flow

```text
Script + Shot List + Call Sheet
        -> Local Parsing
        -> AI Structured Extraction / Issue Detection
        -> Production Manager Review
        -> Confirmed Requirements
        -> PREVENT Rule Engine
        -> Readiness Score + Status + Actions
```

### 6.2 AI Responsibilities

AI may:
- extract candidate requirements,
- identify incomplete information,
- detect potential document inconsistencies,
- identify possible contingency gaps,
- recommend actions,
- provide confidence values.

AI may not:
- compute the final readiness score,
- silently alter project data,
- directly create hard constraints,
- automatically reschedule production.

### 6.3 AI Output

AI output must be validated structured JSON through Pydantic.

Example concept:

```json
{
  "scenes": [
    {
      "scene_number": "05",
      "detected_requirements": [
        {
          "category": "WEATHER",
          "name": "Daylight outdoor condition",
          "source_reason": "Scene heading contains EXT. DAY",
          "confidence": 0.86,
          "suggested_hard_constraint": true
        }
      ],
      "issues": [
        {
          "severity": "WARNING",
          "category": "CONTINGENCY",
          "title": "No outdoor contingency found",
          "description": "No fallback scene is defined if the outdoor scene cannot proceed.",
          "recommended_action": "Prepare a weather-independent fallback scene.",
          "confidence": 0.91
        }
      ]
    }
  ]
}
```

Unknown scene/resource references must be rejected or sent back for human review.

### 6.4 Confidence Display

- >= 0.80: High-confidence suggestion
- 0.60–0.79: Medium confidence / needs review
- < 0.60: informational suggestion

Confidence does not directly affect readiness score.

### 6.5 Readiness Categories and Weights

- Shot / Scene Completeness: 20%
- Cast Readiness: 15%
- Equipment Readiness: 15%
- Location Readiness: 10%
- Schedule Feasibility: 15%
- Quality Requirements: 15%
- Contingency Readiness: 10%

Requirement scoring:
- SATISFIED = 1.0
- UNKNOWN = 0.5
- FAILED = 0.0

Category score is the mean of applicable requirements multiplied by 100.

Weighted score is the sum of category score × category weight.

Issue penalties:
- Critical non-blocking issue: -10
- Warning: -3
- Missing confirmation: -2
- Penalty capped at 20 points.

Final readiness:

`max(0, weighted_score - penalty)`

### 6.6 Readiness Status

READY:
- score >= 85,
- no hard blocker,
- no open critical issue,
- no important unknown requirement.

NEEDS REVIEW:
- no hard blocker, but score < 85, or warnings/open confirmations remain.

NOT READY:
- any confirmed hard constraint is FAILED,
- schedule is infeasible,
- mandatory resource is unavailable.

Hard blockers override numerical score.

### 6.7 Suggestions

For each issue, user may:
- Edit Manually
- Apply Suggestion

Apply Suggestion flow:

```text
Issue -> Proposed Patch -> Preview -> Confirm / Cancel
```

No direct AI mutation is allowed.

- Imported Call Sheet
- Generated Schedule from scenes/resources/constraints

### 7.2 Granularity

- PREVENT analyzes shot-level details.
- RECOVER schedules scene-level blocks.

### 7.3 Hard Constraints

- cast availability
- equipment availability
- location availability
- work hours
- setup time
- travel time
- scene dependencies
- equipment requirements
- actor requirements
- lighting requirements
- audio requirements
- weather/location conditions
- completed scene locks

Completed and currently in-progress scenes are locked by default.

## 8. Live Production

Available actions:
- Start Scene
- Complete Scene
- Block Scene

System records planned and actual times and computes delay.

When delay creates meaningful schedule risk, show a warning and offer:
- Generate Recovery Plans
- Continue Current Schedule

No automatic replanning.

## 9. Incident Reporting

Hybrid form:
- category
- affected resource/location/scene
- current status
- estimated duration
- free-text description

AI parses only ambiguous/free-text context.

Possible incident categories:
- equipment failure
- cast delay
- weather/location disruption
- equipment delivery delay

Uncertain AI-extracted facts require confirmation before becoming authoritative solver input.

## 10. RECOVER Engine

### 10.1 Flow

```text
Incident
 -> Verified Production State
 -> Shootability Check
 -> OR-Tools CP-SAT
 -> Fastest / Cheapest / Minimum Change
 -> Cost Engine
 -> AI Explanation
 -> Production Manager Review
 -> Final Validation
 -> Schedule Version
 -> Updated Call Sheet
 -> Crew Impact / Notification
```

### 10.2 Shootability

A scene is eligible for a slot only when all confirmed hard requirements are satisfied for that slot.

Examples:
- required actor available,
- required camera available,
- location available,
- lighting available,
- weather requirement satisfied,
- audio requirement satisfied,
- setup/travel constraints satisfied.

### 10.3 Recovery Objectives

Run solver separately three times.

FASTEST:
- minimize production finish time.

CHEAPEST:
- minimize additional recovery cost.

MINIMUM CHANGE:
- minimize disruption to current schedule.

Initial stability penalties:
- same day / same slot: 0
- same day shifted: 1
- moved to another day: 3
- changed location: 4
- deferred: 10

These are tunable MVP parameters.

### 10.4 User Priority

Production Manager chooses:
- TIME
- COST
- STABILITY

All three plans remain visible. Priority only changes ordering/recommendation.

### 10.5 AI Explanation

After deterministic results exist, AI receives summarized plan data and writes a human-readable trade-off explanation.

AI may not alter solver-generated values.

### 10.6 Partial / Unresolved Plans

If some scenes cannot be scheduled:
- action = UNRESOLVED
- plan status = DRAFT
- Approve & Apply disabled

A plan with unresolved hard constraints can be saved but not activated.

### 10.7 Outdated Plans

Every recovery plan stores `base_state_version`.

Approval requires current project production state version to match the recovery plan version.

If different:
- reject approval,
- return `RECOVERY_PLAN_OUTDATED`,
- require regeneration.

## 11. Cost Engine

Medium-detail cost model:
- crew overtime
- additional equipment rental
- location extension
- extra transport / location moves
- additional shooting time costs not already counted elsewhere

Use resource-specific rate when present; otherwise project defaults.

Avoid double counting costs already included in baseline project commitments.

## 12. Weather Integration

Use a provider adapter.

Default provider:
- Open-Meteo

Input location:
- name + full address

Forecast is supporting information only.

Actual manually reported weather is authoritative for current production state.

## 13. Crew Coordination

After a new schedule becomes ACTIVE:
- compare previous and new schedule,
- identify affected cast/crew,
- preview notification,
- optionally send through Resend,
- otherwise use demo email mode.

Crew members do not log in.

A unique confirmation URL allows:
- AVAILABLE
- UNAVAILABLE

An UNAVAILABLE response updates availability. If it invalidates the active schedule, SetRescue shows `Schedule No Longer Valid` and lets the Production Manager manually regenerate recovery plans.

## 14. AI Configuration

Provider-agnostic OpenAI-compatible adapter.

Configurable:
- provider name
- base URL
- model
- API key

The application includes an AI Settings page and Test Connection action.

API key storage:
- encrypted in SQLite with Fernet or equivalent,
- encryption key stored separately in local environment configuration,
- never returned to frontend after save.

No special AI offline product mode is required.

Normal failure behavior:
- one automatic retry,
- structured error after final failure,
- explicit Retry action in UI.

AI cache is used for token efficiency, not as a user-facing offline mode.

## 15. Token Efficiency

- Parse PDF/XLSX locally.
- Hash document sections.
- Reuse AI results when input/context hashes remain valid.
- Reanalyze only changed sections where possible.
- Log input, output, total tokens, duration, cache hit, and operation type.

Do not claim a percentage of token savings until measured through actual runs.

## 18. API Contract

Success:

```json
{
  "success": true,
  "data": {},
  "error": null
}
```

Failure:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "RECOVERY_PLAN_OUTDATED",
    "message": "Production conditions have changed.",
    "details": {}
```

- `/api/projects`

## 20. Approval Transaction

Recovery approval must be atomic:

```text
BEGIN
1. verify state version
2. revalidate hard constraints
3. verify zero unresolved scenes
4. create new schedule version
5. mark old active schedule superseded
6. mark new schedule active
7. persist approval
8. increment production state version
COMMIT
```

Rollback on failure.

## 21. File Handling

Validate extension/MIME/signature where practical.

Store with generated safe file names, not direct user-supplied paths.

## 24. Acceptance Criteria

### PREVENT
- Text-based PDF and XLSX upload works.
- Script/Shot List/Call Sheet extraction works.
- Structured data is editable.
- AI suggestions can be confirmed or rejected.
- Rule engine computes score/status.
- Hard blockers override score.
- Apply Suggestion always previews before commit.
- PREVENT report PDF works.
- Token usage is recorded.

### RECOVER
- Hybrid incident entry works.
- Confirmed incident updates production state.
- Completed scenes remain fixed.
- Hard constraints are always enforced.
- Three objective plans are generated when feasible.
- Cost breakdown is auditable.
- Unresolved plans remain DRAFT.
- DRAFT plan cannot be applied.
- Outdated plan cannot be approved.
- Approval creates a new schedule version.
- Updated Call Sheet PDF works.
- Crew impact is calculated.
- Demo email preview works.
- Crew UNAVAILABLE response can invalidate a schedule.

### Token Efficiency
- unchanged document content reuses valid cache,
- changed content triggers only relevant reanalysis where possible,
- usage metrics record actual API calls and token counts.
